# spec.md の作成

製品・機能が何を満たすべきかを、日本語で検証可能な仕様にまとめる。

## 保存先と参照元

- 作業先の AGENTS.md を確認し、配置規則と編集範囲に従う。
- このプロジェクトでは docs/plans/ の「通し番号_計画タイトル」配下に spec.md を置く。既存 plan の通し番号は数値で比較し、最大のものを現在の plan とする。過去の plan は参照しない。
- 実装完了後の新しい変更では、既存の最大番号に1を加えた plan を作成する。作業対象や完了状況を判断できない場合は、ユーザーに確認する。
- plan がまだなければ、依頼内容に合うタイトルで 1_計画タイトル を作成する。
- ユーザーの依頼、現在の plan 内の文書、必要に応じて ARCHITECTURE.md と関連コードを確認する。WORK_LOG.md は仕様や許可の根拠にしない。
- 既存の spec.md を更新するときは、依頼に関係する箇所を修正し、他の合意済み要件を保持する。

## 仕様の整理

- ユーザーが明示した要件と、既存実装から確認した現状を区別する。現在の動作を、根拠なく新しい要件として扱わない。
- 目的、利用者、対象範囲、主要な操作と結果を整理する。重要な不明点は質問し、未回答の事項は「未確定事項」に残す。
- 推奨案や仮定は確定した要件と区別する。回答が必要な項目を独断で確定しない。
- 要件には参照可能な ID（例: FR-001）を付け、条件、入力、期待する動作・出力を具体化する。関連するエラーや境界条件も含める。
- 「高速」「使いやすい」などの曖昧な条件は、必要な場合に測定方法や基準を確認する。数値目標を勝手に作らない。
- 実装方法やライブラリの選択は原則として design.md の責務とする。ただしユーザーが指定した技術的制約は仕様にも明記する。

## 推奨構成

依頼の規模に合わせて見出しを調整し、不要な項目を無理に増やさない。

```markdown
# 機能・製品名の仕様

## 目的・背景

## 対象ユーザー・利用場面

## 対象範囲
### 対象
### 対象外

## 機能要件

## 入出力・データ

## 異常時・境界条件の動作

## 非機能要件・制約

## 受け入れ条件

## 未確定事項
```

受け入れ条件は、関連する要件 ID と対応させ、前提・操作・期待結果など、確認できる形で書く。未確定事項には、決定が必要な内容とその影響を記載する。

## 完了確認

- 依頼の各要件が仕様に反映され、受け入れ条件から確認できるかを見直す。
- 用語、要件 ID、本文と受け入れ条件の間に矛盾がないかを確認する。
- 仕様作成の依頼だけで実装、設定変更、外部サービスへのアクセスを始めない。
- プロジェクトのルールに従って WORK_LOG.md に作業内容を追記する。
- 完了報告では保存先、整理した内容、残る未確定事項を簡潔に伝える。
